# IMU 유실 원인 추적 — 작업 지시

**작성 2026-10-29, 개정 2026-10-30.** 원인 미확정. 전원을 완전히 연결한 상태에서
재현 측정부터 시작한다. 찾았다고 생각하면 **§6 반증 3종을 모두 통과해야** 결론으로 적는다.

`CLAUDE.md` 전체. 특히 "Before any measurement: the ghost-publisher check".
이 조사는 §7.1 유령 발행자 사건과 같은 종류의 함정(측정 지표 자체가 틀림)에 두 번 빠졌다.

## 1. 무엇을 찾는가

`state_estimation_ekf_node` 가 `/raw/imu_6dof` 샘플의 `header.stamp` 간격이 50 ms 를
넘을 때 남기는 경고의 **원인**:

```
[EKF] IMU 샘플 13개분 유실 (dt=130.0 ms, 누적 1회) -> 실측 dt로 적분
```

코드 `state_estimation_ekf_node.cpp:759` (`DT_LONG_SEC = 0.05`).

### 데이터는 사라지지 않는다 — 늦게 온다

`uart_bridge_node` 의 10 ms 폴링 타이머가 밀리면 그 사이 nRF 패킷이 커널 버퍼에
쌓이고 한꺼번에 들어온다. 시각이 함께 오므로 EKF 는 실측 `dt` 로 적분해 각도는 정확하다.
**오늘 당장의 고장은 아니다.**

### 왜 그래도 찾는가

각속도 기반 피치 제어를 넣을 예정이다. 각속도는 "지금 값"이 필요해 100 ms 전 값을
쓰면 제어가 틀린다. 가드로 막을 수는 있으나(§7), 원인을 알면 가드가 거의 발동하지
않게 만들 수 있다.

### 결정적 전제 — 범위가 이미 좁혀져 있다

**`dt` 는 nRF 의 샘플 시각이 아니라 Pi 의 도착 시각이다.**
`uart_bridge_node.cpp:214` 가 `this->now()` 로 스탬프를 찍는다
(`state_estimation_ekf_node.cpp:726` 주석이 이 사실을 명시).

따라서 유실은 **`uart_rx_loop` 가 호출된 시각의 간격**이다. 다만 이 지표만으로는
"nRF 가 늦게 보냄" 과 "Pi 가 늦게 읽음" 이 **구분되지 않는다** — 둘 다 같은 증상이다.
구분은 §5 단계 2 에서 nRF 패킷 카운터 또는 UART 인터럽트로 한다.

## 2. 측정 방법 — 여기서 두 번 틀렸다. 반드시 지켜라

### 함정 1 (치명적): 로그 줄 수를 세면 안 된다

경고는 `RCLCPP_WARN_THROTTLE(..., 5000, ...)` — **5초에 한 줄만** 찍힌다.
줄 수는 "유실이 있었던 5초 구간의 개수"이고 유실 횟수가 아니다.
이 착각으로 "hydro 가 원인, 1→8회" 라는 **틀린 결론을 두 번 재현까지 하고 보고했다.**

**메시지 안의 `누적 N회` 를 읽어라.** 이것이 `dt_long_count_` 실제 카운터다.

```bash
cum() { grep -o '누적 [0-9]*회' "$1" | tail -1 | grep -o '[0-9]*' || echo 0; }
```

`dt > 0.5 s` 는 별도 카운터(`dt_break_count_`, "스트림 단절")다. **같이 읽어라.**

```bash
brk() { grep -o '단절 (dt=[0-9.]* s, 누적 [0-9]*회' "$1" | tail -1 | grep -oE '[0-9]+회' | grep -o '[0-9]*' || echo 0; }
```

### 함정 2: 노드 생존을 확인하지 않으면 측정이 무효다

EKF 가 측정 중간에 죽은 채 "10분 유실 0회" 를 보고한 적이 있다.
**측정 구간 내내 1분마다 생존을 기록하라.**

```bash
ps -C state_estimation -o pid= --no-headers | wc -l   # 1 이어야 한다
```

### 함정 3: 데이터가 안 와도 유실은 0 이다

**수신율을 같이 재라.** `/raw/imu_6dof` 가 100 Hz 근처여야 측정이 유효하다.

```bash
timeout 25 ros2 topic hz /raw/imu_6dof   # average rate 100 근처
```

### 함정 4: `pkill -f` / `pgrep -f` 는 자기 셸을 죽인다

패턴이 자신의 명령줄에도 걸려 exit 144 로 끝난다. **세 번 당했다.**
PID 를 지정해 kill 하라.

```bash
for p in $(ps -C uart_bridge_node,i2c_driver_node,state_estimation,pid_control_nod,\
hydro_estimator,data_logger_nod,rpm_driver_node,auto_scenario_n -o pid= --no-headers); do
  kill $p 2>/dev/null
done
```

### 함정 5: `ros2 launch` 는 죽은 자식을 되살린다

노드만 kill 하면 PID 가 바뀌어 살아난다. **launch 감독 프로세스를 먼저** 잡아라
(`ps -C ros2 -o pid=,args=` 로 PID 를 찾아 지정).

### 함정 6: sudo 비밀번호가 필요하다

`sudo systemctl {start,stop,restart} fish-robot` 를 **실행할 수 없다. 사용자에게 요청하라.**
수동 기동은 `ros2 launch fish_robot_pkg fish_robot.launch.py` 로 가능하다.
**서비스가 떠 있으면 수동 기동 금지** — `/dev/ttyAMA0`, I2C, GPIO 21 을 두 copy 가 다툰다.

### 함정 7: 측정 로그를 지워라

측정마다 `log_csv/` 에 수십 MB 가 쌓인다. 끝나면 지워라.
`log_csv/` 는 실험 CSV 도 보관하는 곳이라 자동 삭제가 없다(의도된 설계).

## 3. 확정된 사실 — 다시 재지 말 것

### 유실은 실재한다 (10-29 00:45 서비스 기동분, 11분 7초, 누적 130회)

```bash
journalctl -u fish-robot --since "2026-10-29 00:00" --no-pager \
  | grep "유실" | sed -E 's/.*([0-9]{2}:[0-9]{2}:[0-9]{2}).*dt=([0-9.]+) ms, 누적 ([0-9]+)회.*/\1  dt=\2ms  누적\3/'
```

- 주기 **7~15초마다 1회**, 크기 **50~123 ms** (5~12 샘플분)
- **11분 내내 고르게** — 분당 4~8회 (아래 "기각된 가설" 참조)
- `AUTO` 주행 없음 (CSV `State` 전부 0), RPM 0, 조종기 끊김(`RC_T`=-9999 100 %)
- **`VBat` 22.67 V — 배터리는 연결돼 있었다**
- 전체 수신율은 정상: 65938행 / 665초 = **99.1 Hz**

### 로거 구멍과 EKF 유실은 76 % 불일치한다 — 핵심 단서

`data_logger_node` 는 타이머가 없고 `/filtered/attitude` 콜백에서 한 행을 쓴다
(`data_logger_node.cpp:135`). 10-29 로그의 행 간격 > 50 ms 는 60개.

| | 개수 |
|---|---|
| journal 유실 줄 | 72 |
| 로거 구멍과 ±2 s 안에 겹친 것 | **17 (24 %)** |

→ EKF 는 **입력(UART 도착)이 밀렸는데도 출력(발행)은 100 Hz 를 유지**했다.
밀린 것은 `uart_bridge_node` 의 타이머 하나이고, 밀린 뒤 쌓인 패킷을 한 번에
처리해 평균 레이트를 복구했다.

**이것이 "시스템 전역 CPU 부하" 가설과 상충한다** — 전역 부하면 EKF 와 로거도 같이 밀려야 한다.

## 5. 작업 순서

### 단계 0 — 전원·환경을 기록하라 (측정 전 필수)

재현 여부와 무관하게 **매 측정의 환경을 남겨야** 비교가 가능하다.

```bash
date -Is
vcgencmd measure_temp; vcgencmd get_throttled    # 0x0 이 정상
nproc; uptime
cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor 2>/dev/null
systemctl list-timers --all | head -20            # 임박한 정기작업
systemctl is-active fish-robot
i2cget -y 1 0x68 0x75                             # 0x71 이어야 9축 (J4 확인)
```

`vcgencmd get_throttled` 가 0x0 이 아니면 **그것을 먼저 해결**하라 — 스로틀링은
타이머 지연의 충분한 원인이고, 다른 모든 측정을 오염시킨다.

### 단계 1 — 재현시켜라

**사용자에게 서비스 기동을 요청한다**(sudo 필요, 함정 6).
전원을 완전히 연결한 상태 = nRF 배터리 + 모터 배터리.

- **기동 직후 t=0 부터 센다.** 10-29 는 기동 20초 후 첫 유실이 났다.
  안정화 구간을 건너뛰면 놓친다.
- **최소 20분.** 10-29 는 11분에 130회였다. 20분에 0회면 재현 실패로 판정.
- 측정 중 **1분마다** 누적·생존·온도를 기록한다.

```bash
# 측정 루프 예시 (서비스 journal 을 읽는다)
for i in $(seq 1 20); do
  sleep 60
  C=$(journalctl -u fish-robot --since "-70s" --no-pager | grep -o '누적 [0-9]*회' | tail -1 | grep -o '[0-9]*')
  E=$(ps -C state_estimation -o pid= --no-headers | wc -l)
  T=$(vcgencmd measure_temp)
  echo "${i}분: 누적=${C:-변화없음} EKF=$E $T $(vcgencmd get_throttled)"
done
```

**재현되면 그 순간의 상태를 반드시 같이 잡아라 — 이것이 핵심 데이터다:**

```bash
SC=/tmp/claude-1000/.../scratchpad
# ① 무엇이 CPU 를 먹는지 (1초 간격 20분)
top -b -d 1 -n 1200 -o %CPU > $SC/top.log &
# ② uart_bridge 프로세스의 스케줄 지연·코어 (pidstat 없으면 ③ 로)
P=$(ps -C uart_bridge_nod -o pid= --no-headers)
pidstat -p $P -w -u 1 1200 > $SC/pidstat.log 2>&1 &
# ③ 어느 코어에서 돌는지 + 비자발적 컨텍스트 스위치
while :; do
  echo "$(date +%s) $(ps -o psr=,nvcsw=,nivcsw= -p $P --no-headers)" >> $SC/core.log
  sleep 1
done &
# ④ UART 인터럽트 증가량 (10-29 와 비교할 기준선이 없으니 지금 만들어 둔다)
while :; do echo "$(date +%s) $(grep -iE 'uart|ttyAMA|serial' /proc/interrupts)" >> $SC/irq.log; sleep 5; done &
```

유실 시각과 ①~④ 를 **시간축으로 대조**하라. 유실 순간에
- 특정 프로세스의 CPU 가 튄다 → 그 프로세스가 범인
- `nivcsw`(비자발적 스위치)가 튄다 → 스케줄링
- `psr`(코어)이 바뀐다 → 코어 마이그레이션
- UART 인터럽트가 멈춘다/몰린다 → 드라이버·하드웨어

### 단계 2 — nRF 측 vs Pi 측 구분 (재현된 경우)

스탬프만으로는 구분이 안 된다(§1). 두 방법 중 하나로 가른다.

- **UART 인터럽트**: 유실 구간에 `/proc/interrupts` 의 UART 카운트가
  **계속 증가**하면 nRF 는 보냈고 Pi 가 읽지 못한 것 → **Pi 측**.
  **증가가 멈추면** nRF 가 보내지 않은 것 → **nRF 측**.
- **커널 버퍼**: 유실 직후 한 틱에 읽히는 바이트 수가 46 의 배수로 뭉쳐 오면
  버퍼에 쌓였던 것 → **Pi 측**. `uart_bridge_node` 에 임시 로그를 넣어 확인
  (`read()` 반환 누적 바이트/틱). **커밋하지 말고 측정 후 되돌려라.**

### 단계 3 — 재현 안 되면 (20분 0회)

재현 없이 원인을 확정할 수는 없다. 대신 **범위를 줄이는** 실험을 한다.
각 10분, 대조군(부하 없음)은 이미 0회로 측정됨.

1. **국소 부하**: `uart_bridge_node` 가 도는 코어만 점유.
   ```bash
   P=$(ps -C uart_bridge_nod -o pid= --no-headers); C=$(ps -o psr= -p $P --no-headers)
   taskset -c $C sh -c 'while :; do :; done' &   # 그 코어만 100 %
   ```
   유실이 나면 **"국소 부하" 가설 확정** — 10-29 에 그 코어를 먹은 것을 찾으면 된다.
2. **전역 부하**: 4코어 전부.
   ```bash
   for i in 1 2 3 4; do (while :; do :; done) & done
   ```
   여기서만 나면 전역 부하이고, "로거 76 % 불일치" 와 모순되므로
   **10-29 의 원인은 아니다** — 다른 것을 찾아야 한다.
3. **실시간 우선순위**: 유실이 재현되는 조건에서 `uart_bridge_node` 에 RT 를 주고
   사라지면 스케줄링으로 확정(sudo 필요 — 사용자 요청).
   ```bash
   sudo chrt -f 50 -p $(ps -C uart_bridge_nod -o pid= --no-headers)
   ```
4. **시간대 재현**: 10-29 는 심야 00:45 이었다. 같은 시각에 20분 측정해
   그때만 나면 정기작업 가설로 되돌아간다(§4 에서 시간대 불일치로 기각했으나,
   `apt` 가 다운로드한 것을 나중에 처리하는 등 2차 효과는 배제되지 않았다).

### 단계 4 — 조사가 막히면

**확정 못 함을 기록하는 것도 결과다.** §4 표에 시도·기각을 추가하고 멈춰라.
각속도 제어(§7)는 이 결과와 무관하게 진행 가능하다. 억지 결론을 적지 마라.

## 6. 검증 — 원인을 찾았다고 생각하면 반드시

**이 조사에서 두 번 틀렸다. 세 번째를 만들지 마라.**
한 번은 측정 지표가 틀렸고(함정 1), 한 번은 재현 없이 철회했다.

검증은 "맞는 증거 찾기" 가 아니라 **반증 실험**이다. 세 가지를 **모두** 통과해야 한다:

1. **켜고 끄기 (양방향)**: 원인을 제거하면 유실이 **0 이 되고**, 되돌리면 **다시 난다**.
   각 10분 이상, 각 2회. 한 방향만 보고 끝내지 마라 —
   "hydro 붙이면 8, 떼면 1" 을 두 번 재현했는데도 틀렸다.
2. **용량-반응**: 원인의 크기를 키우면 유실이 **비례해서** 늘어난다.
   (예: 국소 부하 1코어 → 2코어에서 유실도 증가)
3. **지표 교차 확인**: `누적 N회` 외에 **독립적인 두 번째 지표**가 같은 결론을
   가리켜야 한다. 후보:
   - CSV 행 간격 > 50 ms 개수 (단 76 % 불일치를 염두에 둘 것 — §3)
   - `top` 의 프로세스별 CPU
   - `nivcsw` 비자발적 컨텍스트 스위치
   - `/proc/interrupts` UART 증가량

**하나라도 어긋나면 원인이 아니다.** 단계 1 로 돌아가라.

추가 점검: 결론이 §3·§4 의 확정 사실과 모순되지 않는지 확인하라. 특히
**"로거 76 % 불일치"** 와 **"과거 15회는 0.0~0.4회/분"** 두 가지는 전역·상시
원인을 배제한다. 거기에 걸리는 결론이면 다시 생각하라.

## 7. 조사와 무관하게 확정된 것 — 건드리지 말 것

각속도 피치 제어는 이 조사 결과와 **독립적으로** 진행 가능하다. 설계는 확정됐다.

| 파라미터 | 기본값 | 근거 |
|---|---|---|
| `kp_pitch_angle` | 4.0 (°/s)/° | 각도 오차 10° 에서 `pitch_rate_max` 도달 |
| `kp_pitch_rate` | **0** µs/(°/s) | 0 = 기존 동작과 동일. 자이로 부호 벤치 확인 후 켠다 |
| `pitch_rate_max` | 40 °/s | 10-19~10-26 주행 실측: 기동 중 p95 29.5 < 40 < p99 60.3 |
| `pitch_rate_lpf_tau` | 0.05 s | `straight`(목표 0°) 에서도 꼬리 비트로 p50 4.8 °/s 가 뜬다 |
| `pitch_rate_max_age` | 0.05 s | 실측 유실 50~123 ms 를 덮는다 |

- EKF 가 `w_hat = gyro_rad - b_` (`state_estimation_ekf_node.cpp:794`) 를
  `/filtered/angular_rate` (Vector3, °/s, FLU) 로 발행한다.
  `attitude_pub_->publish(att)` (`:1398`) 옆에 두어 타임스탬프를 맞춘다.
- I·D 는 각도 오차 기준을 유지한다. P 항만 바꾼다
  (ki/kd 가 전부 0 이라 지금은 무영향이고, 각속도 D = 각가속도는 잡음이 심해 별도 설계가 필요).
- 가드는 유실 때문이 아니라 **고장 대응**(노드 사망·UART 두절)으로 어차피 필요하다.
  원인이 밝혀져도 가드는 남긴다.
- **`hydro_estimator_node` 는 생자이로를 계속 쓴다.** 필터값으로 바꾸면 바이어스가
  빠져 정지 시 `|ω|` 가 6.2~6.5 → 0 근처로 내려가고 문턱 7 dps 가 무의미해진다.
  CSV 의 `BiasX/Y/Z` 는 10 Hz 계단값이라 과거 로그로 재측정도 불가능하다.
  10-29 에 95회로 검증한 대기창 영점을 무효화한다 — **하지 마라.**
- **자이로 피치 축 부호 벤치 확인은 물 시험 전 필수.** 부호가 거꾸로면 제동이
  가속이 되어 발산한다. 이 로봇은 **양수 피치 = 코가 아래**(항공 관례의 반대).
  방법: 서비스 기동 후 `ros2 topic echo /filtered/angular_rate`, 손으로 코를 내려
  부호 확인. **사용자가 직접 해야 한다**(서비스 기동에 sudo 필요).
